ATC Office (901) Access Sync

How ATC Office becomes a full inventory property: the 901_wh App Role, the InvApp_ATC_Office group, and the Azure Automation runbook that keeps the group in step with the 901 Teams channel.

01

Overview

ATC Office (PropCode 901) is a real inventory property, so corporate can track and request what it needs. Before this change it had no App Role, and only DatabaseManager users could write there.

Rule: anyone in the private 901 channel of the ATC Development team may use every inventory function at ATC Office once they complete training.

A Teams channel cannot be assigned an App Role (only users and Entra groups can), and a dynamic group cannot follow channel membership (dynamic rules evaluate user attributes only). An hourly Azure Automation runbook therefore copies the channel's members into a security group that holds the 901_wh role.

1 →A person is added to (or removed from) the private 901 channel, by IT or a channel owner
2 →Within the hour, runbook Sync-901ChannelToInvAppGroup adds them to (or removes them from) InvApp_ATC_Office
3 →InvApp_ATC_Office is assigned to App Role 901_wh on ATC_InventoryAPI
4 →At their next sign-in the token carries 901_wh: write scope at ATC Office
5 →After training, IT adds them to InvApp_Users (manual, unchanged): required to write in Live

One-Time Setup

Complete in order. Entra changes apply to Test and Live at once (one shared app registration). Database rows are per environment (section 09).

Step 1 — Create the App Role

Entra admin center → App registrations → ATC_InventoryAPI → App roles → Create app role.

Display nameATC Office
Allowed member typesUsers/Groups
Value901_wh
DescriptionProperty staff access for ATC Office
EnabledYes
ℹ️
Role values may contain digits, letters and _, so 901_wh is valid. The value must be exactly 901_wh: the API (IsInRole) and the PWA (canWriteToWarehouse) both compare {PropCode}_wh case-sensitively.

Step 2 — Create the security group and assign it to the role

  1. Entra admin center → Groups → New group: type Security, name InvApp_ATC_Office, membership type Assigned, Microsoft Entra roles can be assigned to the group = No. No members yet.
  2. Enterprise applications → ATC_InventoryAPI → Users and groups → Add user/group → select InvApp_ATC_Office → role 901_wh → Assign.
ℹ️
App Role assignments do not pass through nested groups. The runbook adds users directly, so this does not apply.

Step 3 — Create the administrative unit

  1. Entra admin center → Roles & admins → Admin units → Add: name AU-InvApp-ATC-Office, Restricted management = No.
  2. Open the unit → Groups → Add → InvApp_ATC_Office.

Step 4 — Create the managed identity and the Automation account

  1. Azure portal → Managed Identities → Create: resource group PAX8_ATC-Automation, region East US, name mi-invapp-901-sync. Record its Client ID.
  2. Azure portal → Automation Accounts → Create: same resource group and region, name aa-atc-it-automation. On the Advanced tab add mi-invapp-901-sync as a user-assigned identity. Networking: default.
  3. After creation: account → Account Settings → Identity → System assigned → Off → Save. The system identity is never used; leaving it on adds an unused principal.
ℹ️
Why a new account: Automation account names cannot be changed. The existing account ATC-Leadership-Rocks was built for an unrelated job, so this runbook was not placed there. aa-atc-it-automation is the home for future IT automation runbooks.

Step 5 — Grant read-only Graph permissions to the identity

Managed identities have no consent screen; app permissions are granted by script. Run once from an admin workstation (needs the Microsoft.Graph.Applications module and an account that can grant app role assignments):

Connect-MgGraph -Scopes 'AppRoleAssignment.ReadWrite.All','Application.Read.All'

$mi    = Get-MgServicePrincipal -Filter "displayName eq 'mi-invapp-901-sync'"
$graph = Get-MgServicePrincipal -Filter "appId eq '00000003-0000-0000-c000-000000000000'"

foreach ($perm in 'ChannelMember.Read.All', 'GroupMember.Read.All') {
    $role = $graph.AppRoles | Where-Object {
        $_.Value -eq $perm -and $_.AllowedMemberTypes -contains 'Application'
    }
    New-MgServicePrincipalAppRoleAssignment -ServicePrincipalId $mi.Id `
        -PrincipalId $mi.Id -ResourceId $graph.Id -AppRoleId $role.Id
}
PermissionWhy
ChannelMember.Read.AllRead the 901 channel's members. Read-only. The narrower ChannelMember.Read.Group is a resource-specific consent permission that requires a Teams app installed in the team, so it does not fit a managed identity
GroupMember.Read.AllRead the current members of InvApp_ATC_Office to compare. Read-only
⚠️
Never grant Group.ReadWrite.All or GroupMember.ReadWrite.All to this identity. Either would let it change every group in the tenant and would override the administrative unit scoping in step 6.

Step 6 — Scope write rights to the administrative unit

Entra admin center → Roles & admins → Admin units → AU-InvApp-ATC-Office → Roles and administrators → Groups Administrator → Add assignments → select mi-invapp-901-sync.

Assigned from the unit, the role is scoped to the unit: the identity can change membership of InvApp_ATC_Office and of nothing else. If Privileged Identity Management is in use, the assignment must be Active, not Eligible, because the runbook cannot activate a role.

  1. Automation account → Process Automation → Runtime Environments → Create: name ps74-graph, language PowerShell, version 7.4. Packages tab → add from gallery Microsoft.Graph.Authentication (2.41.2 at setup), the only module the runbook uses. Az and Azure CLI are listed by default and cannot be removed. Create, then wait until the package shows Available. (The built-in environments PowerShell 5.1, 7.1, 7.2 and Python are not used.)
  2. Automation account → Variables → add these (plain, not encrypted; none is a secret):

Step 8 — Import the runbook and schedule it

  1. Automation account → Runbooks → Create: name Sync-901ChannelToInvAppGroup, type PowerShell, runtime environment from step 7. Paste the script from section 05. Save, then Test pane with DryRun = true and review the output.
  2. Test pane with DryRun = false for the first real run; confirm the group membership in Entra. Then Publish (schedules run only the published version).
  3. Runbook → Resources → Schedules → Add a schedule → new schedule Hourly-901-Sync: recurring every 1 hour, no expiration. Parameters: DryRun = false, MaxRemovalPercent blank; run on Azure.

05

Runbook

Behavior

1 →Connect to Graph as mi-invapp-901-sync
2 →Read all channel members (paged). Keep only Entra user members from the ATC tenant whose roles do not include guest
3 →Read all user members of InvApp_ATC_Office (paged)
4 →Add users in the channel but not the group; remove users in the group but not the channel
5 →Write each change and a summary to the job output

Safety rules

SituationResult
Graph call fails (channel or group read)Job fails before any change. Nothing is added or removed
Channel returns no eligible membersJob fails with no change, so an outage or a wrong ID cannot empty the group
More than MaxRemovalPercent (default 50) of the group would be removed in one run, and more than one personJob fails with no change. Confirm the channel is correct, then run once with a higher value
One add or remove failsThe others still apply; the job ends as failed and lists the failures
DryRun = trueReports what would change; changes nothing

Script

<#
  Sync-901ChannelToInvAppGroup
  One-way sync: members of the private 901 Teams channel -> InvApp_ATC_Office
  (assigned to App Role 901_wh on ATC_InventoryAPI).
  Runs as user-assigned managed identity mi-invapp-901-sync.
  Documentation: atc_office_access_sync.html
#>
param(
    [bool]$DryRun = $false,
    [int]$MaxRemovalPercent = 50
)

$ErrorActionPreference = 'Stop'

$teamId       = Get-AutomationVariable -Name 'InvApp901_TeamId'
$channelId    = Get-AutomationVariable -Name 'InvApp901_ChannelId'
$groupId      = Get-AutomationVariable -Name 'InvApp901_GroupId'
$tenantId     = Get-AutomationVariable -Name 'InvApp901_TenantId'
$uamiClientId = Get-AutomationVariable -Name 'InvApp901_UamiClientId'

Connect-MgGraph -Identity -ClientId $uamiClientId -NoWelcome

function Get-AllPages([string]$Uri) {
    $items = @()
    while ($Uri) {
        $page   = Invoke-MgGraphRequest -Method GET -Uri $Uri -OutputType PSObject
        $items += $page.value
        $Uri    = $page.'@odata.nextLink'
    }
    return $items
}

$graph = 'https://graph.microsoft.com/v1.0'

# 1. Channel members: Entra users from this tenant, not guests
$channelUri = "$graph/teams/$teamId/channels/$([uri]::EscapeDataString($channelId))/members"
$wanted = @{}
foreach ($m in (Get-AllPages $channelUri)) {
    if ($m.'@odata.type' -ne '#microsoft.graph.aadUserConversationMember') { continue }
    if ($m.tenantId -ne $tenantId) { continue }
    if ($m.roles -contains 'guest') { continue }
    if ($m.userId) { $wanted[$m.userId] = $m.displayName }
}
if ($wanted.Count -eq 0) {
    throw 'Channel returned no eligible members. No changes made.'
}

# 2. Current group members (users only)
$current = @{}
foreach ($g in (Get-AllPages "$graph/groups/$groupId/members?`$select=id,displayName&`$top=999")) {
    if ($g.'@odata.type' -eq '#microsoft.graph.user') { $current[$g.id] = $g.displayName }
    else { Write-Warning "Ignoring non-user group member $($g.id)" }
}

# 3. Differences
$toAdd    = @($wanted.Keys  | Where-Object { -not $current.ContainsKey($_) })
$toRemove = @($current.Keys | Where-Object { -not $wanted.ContainsKey($_) })

if ($current.Count -gt 0 -and $toRemove.Count -gt 1) {
    $pct = [math]::Round(100 * $toRemove.Count / $current.Count)
    if ($pct -gt $MaxRemovalPercent) {
        throw "Would remove $($toRemove.Count) of $($current.Count) members ($pct%). Limit is $MaxRemovalPercent%. No changes made."
    }
}

# 4. Apply
$failures = @()
foreach ($id in $toAdd) {
    if ($DryRun) { Write-Output "DRY RUN add: $($wanted[$id]) ($id)"; continue }
    try {
        $body = @{ '@odata.id' = "$graph/directoryObjects/$id" } | ConvertTo-Json
        Invoke-MgGraphRequest -Method POST -Uri "$graph/groups/$groupId/members/`$ref" `
            -Body $body -ContentType 'application/json'
        Write-Output "Added: $($wanted[$id]) ($id)"
    } catch { $failures += "Add $id : $($_.Exception.Message)" }
}
foreach ($id in $toRemove) {
    if ($DryRun) { Write-Output "DRY RUN remove: $($current[$id]) ($id)"; continue }
    try {
        Invoke-MgGraphRequest -Method DELETE -Uri "$graph/groups/$groupId/members/$id/`$ref"
        Write-Output "Removed: $($current[$id]) ($id)"
    } catch { $failures += "Remove $id : $($_.Exception.Message)" }
}

Write-Output "Channel: $($wanted.Count) eligible. Group before: $($current.Count). Added: $($toAdd.Count). Removed: $($toRemove.Count). DryRun: $DryRun"
if ($failures.Count -gt 0) {
    throw "Some changes failed:`n$($failures -join "`n")"
}
ℹ️
This page holds the reference copy of the script. If the script is also kept in source control, record the location here and keep both copies in step. Do not store it in the inventory application repositories.

Verification

⚠️
Count members in the Teams admin center, not the Teams client. The Teams client hides disabled accounts; Graph (and therefore the runbook) still returns them. Teams admin center → Teams → Manage teams → ATC Development → Channels → 901 → Members.
  1. Dry run (step 8): the output lists the current channel members as adds; nothing changes. The count must match the Teams admin center.
  2. First real run: every eligible channel member appears in InvApp_ATC_Office.
  3. Add test: add a test user to the 901 channel, start the runbook, confirm the user is in the group. The user signs out and back in to the PWA, opens ATC Office and sees write actions (in Test, without InvApp_Users).
  4. Remove test: remove the test user from the channel, run again, confirm removal from the group. After the next sign-in the write actions are gone.
  5. Scope test (optional): confirm the identity cannot change a group outside the unit. Expect HTTP 403.
