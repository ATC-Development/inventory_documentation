01

Overview

The ATC Inventory Extension is a Manifest V3 Edge extension that fills a vendor's web cart for an Inventory App order list and keeps the Inventory App up to date while the user finishes the order on the vendor's site. It is the fourth component of the ATC Inventory system alongside inventory_api, inventory_pwa and inventory_functions.

The PWA starts a cart session through the API (preflight, which takes the vendor's cart lock) and hands the session to the extension. From then on the extension runs the session on the vendor's site: it waits for the vendor login, fills the cart, reports the cart's contents to the API (reconcile), shows an overlay with the result and a countdown, and ends the session when the user clicks I submitted the order or Release cart, or when the session expires. The PWA can be closed after the fill starts.

ℹ️
Vendor: Fox Appliance Parts — foxparts.com, on the Kodaris B2B platform. The session logic in the background worker is vendor-neutral; each vendor has its own content scripts and configuration (§11).

Two Packages from One Source

The build produces two extensions from the same code. Both are force-installed on every managed device (§12). The PWA addresses each message to the current environment's extension ID, and each extension answers only messages addressed to its own ID (§05).

PackageExtension IDServesVendor
LivemkkkjimbaeioecfkippbplnegmaebdelThe real vendor sites. PWA origin: localhost:5173 only, until the Live environment existsFox site (content scripts, Fox host permission)
TestolmhgecfkfjjleajendeonaeahcfalibThe deployed PWA (Test environment) and localhost:5173, against the Test and local APIsPractice vendor page only (§10). No vendor host permissions: the real vendor is never contacted

The core code (background, bridge, overlay, API client) is shared. Each package's differences are data in its package definition (§08).

What the extension does not do

  • Never deletes vendor cart lines. If the vendor cart is not empty when a fill starts, nothing is added or removed; the fill stops and shows the cart's lines
  • Never creates orders. Its callback token can only update the session's own orders. Extra cart lines are added as orders in the PWA (Add as order), which uses the user's sign-in
  • Stores no vendor credentials; the user logs in to the vendor site
  • Holds one session at a time per browser

Key Constraint — Two Content Script Worlds

The Fox integration uses two content scripts in different execution worlds on foxparts.com:

FileWorldPurpose
content.main.js MAIN Reads the kd global (Kodaris state object), which the isolated world cannot see. Passes csrfToken, isLoggedIn and companyId to the isolated world through window.postMessage. Contains no fetch calls.

⚠️

Architecture

Components

Session States

StateMeaningLeaves by
awaiting_loginVendor tab opened; waiting for the vendor login (login_reason: login_required or wrong_account)Login detected → filling. 15 minutes → ended login_timeout. Vendor tab closed → ended vendor_tab_closed
fillingReading the cart, adding the itemsAdded or failed → reconcile → in_cart. Cart not empty → ended cart_not_empty. Fox refuses the add because its login expired → back to awaiting_login

End reasons: completed, released, expired, closed (the API no longer has the session open: released in the PWA or overridden by a DatabaseManager), cart_not_empty, login_timeout, vendor_tab_closed, failed. The extension releases the cart lock itself for login_timeout, vendor_tab_closed and cart_not_empty (nothing was added).

Durability and Timers

The session record is kept in chrome.storage.session (core/session-store.js), so it survives Edge stopping the service worker. Timers use chrome.alarms: login wait (15 minutes), fill check (2 minutes, finishes a fill whose worker was stopped by reading the cart), and session expiry. Automated steps (vendor page load, identity check, add, cart read) time out after 60 seconds. State changes run one at a time and apply only if the session is still the expected one in an expected state.

ℹ️
correlationId is generated by the PWA for each fill and carried on every push. The PWA applies a push to its panel only when the correlationId and vendor key match its active session.

Message Flow

Fill to Submit

1 →PWA calls POST /vendors/{id}/cart/preflight (user sign-in): validates the orders, takes the cart lock, returns session_id, callback_token, vendor_key, expires_in_seconds and the items
2 →PWA sends start_fill with that payload. The background stores the session and answers accepted at once (or a refusal)
3 →Background opens or focuses the vendor tab (Fox in Live, the practice page in Test) and sends check_identity. Not logged in: the page shows the login banner and the PWA shows Login required. Each reload of that same tab re-checks (E1)
4 →Logged in: fill. The content script reads the cart (viewCart); not empty → stop. Empty → bulk add; the result and the cart's lines go back to the background
5 →Background calls reconcile (trigger fill) with the cart's lines, stores the result, moves the tab to the Fox cart page
6 →Cart tab shown: the overlay lists changes since the last save (no API call). Checkout entered (Cart tab → tab 1 or 2): reconcile (trigger checkout), which also resets the 2-hour expiry
7 →I submitted the order → mark-ordered. Release cart → release. Either ends the session; the token is cleared

Security Model

Approved PWA Origins and API Addresses

The background accepts PWA messages only from the origins in its package's api_origin_by_pwa_origin map (§08), and takes the API address for a session from that same map, keyed by the sending PWA's origin. The API address is never taken from a message. build.js generates the content-bridge matches, externally_connectable.matches and the API host_permissions from the same map, so they cannot disagree.

PackagePWA originAPI
Livehttp://localhost:5173http://localhost:5077
Testhttp://localhost:5173http://localhost:5077
https://gray-tree-0fe80630f.4.azurestaticapps.nethttps://atc-inventory-api-fhadavctbwbqace3.eastus-01.azurewebsites.net (Test API)

The Live package does not recognize the deployed PWA until the Live environment exists: its bridge is not injected there, and the background refuses that origin.

content-bridge.js Filtering

The content-bridge only forwards messages that pass all of these checks:

  • event.source === window — same window only
  • event.origin === PWA_ORIGIN — same origin only
  • data.source === 'ATC_PWA' — correct source tag
  • data.targetExtensionId === chrome.runtime.id — addressed to this extension. Both packages can be installed on the same PWA origin (localhost), and both bridges receive every message; the other one stays silent. An empty target (environment not configured) is answered by neither
  • ALLOWED_TYPES: ping, start_fill, end_session. Pushes forwarded to the page: cart_session

The bridge forwards only type, requestId, correlationId, vendorKey and payload. A background's pushes reach only its own extension's bridge.

Vendor page messages are accepted only from this extension's content scripts on the session vendor's origin, or from this extension's practice page for the session's vendor key (§03).

Sensitive Values

ValueHandling
callback_tokenFrom preflight, passed to the extension once in start_fill. Kept only in the background's session record in chrome.storage.session (in memory, cleared when the browser closes, not readable by content scripts at the default access level). Extension pages can read that storage area; the practice page uses only its own keys and never reads the session record. Never sent to a content script or back to the PWA; sent only to the built-in API address. Cleared when the session ends. The API stores only its hash
What the token allowsReconcile, mark-ordered, release and leftovers for that one session, while open and unexpired. It cannot create records
Fox session cookiesHttpOnly — never accessible to JavaScript in any world
CSRF token (kd.csrfToken)Read in the MAIN world, used by the ISOLATED world for the add request only; not stored

No Stored Credentials

The extension stores no vendor credentials. The user logs in on the vendor site. The extension reads only the identity state the vendor's page exposes (kd.customer.isLoggedIn, kd.customer.selectedCompanyID). Because that page state can be stale, a Fox refusal of the add (HTTP 401/403 or "Unauthorized") is treated as login required.

All overlay and practice page text is set with textContent; part names, codes (including codes typed on the practice page) and Fox error text are never parsed as HTML.

Fox Parts — Platform Details

Fox Appliance Parts runs on the Kodaris B2B e-commerce platform. All discoveries below were confirmed by live testing against an authenticated ATC session. This section applies to the Live package; in Test, the practice page stands in for Fox (§10).

Identity Detection

Kodaris exposes a kd global object on every page via an inline script block. It is not attached to window and must be accessed directly. Two fields are used for identity verification:

kd.customer.isLoggedIn        // boolean
kd.customer.selectedCompanyID  // ATC's company ID: 2771
kd.csrfToken                   // Required as X-CSRF-TOKEN header on mutating requests
ℹ️
kd is only accessible from the MAIN world. The isolated world cannot read it directly. content.main.js reads it and passes the values to content.isolated.js via window.postMessage.

Fox Endpoints Used

MethodEndpointPurpose
GET/api/user/cart/viewCartRead the cart: orderID and orderItems[] (code, quantity, orderItemID). No CSRF token needed
POST/api/user/cart/item/bulkAdd items by code and quantity (X-CSRF-TOKEN required). On success the response data is the updated cart. On a bad code Fox stops at it and returns its error text; the extension then reads the cart to see what was added

No Cart Deletion

The extension never deletes Fox cart lines. A fill starts only on an empty cart: if viewCart returns any line, the fill stops (cart_not_empty), the lines are shown on the overlay and in the PWA, and the session's cart lock is released. Lines left in the cart by an ended session are removed by hand on Fox.

Cart Page Tabs

/spcu/cart is one page with three tabs (.cv-tab, active one .cv-tab--active): 0 Cart, 1 Addresses, 2 Delivery and payment. Changing tab does not reload the page. While the session is in the cart, the content script watches the active tab:

MomentWhat happensAPI calls
Cart tab shownCart read; overlay lists what changed since the last save0
Checkout entered (Cart → tab 1 or 2)Cart read and reconciled (checkout); 2-hour expiry reset. Moving between tabs 1 and 2 is not a new entry1

Overlay

In the cart: matched count, items not in the cart, quantity changes, lines not in this order (with a pointer to Add as order in the Inventory App), Fox errors, last save time, the YARDI → PO → place order steps, and Time left (red at 15 minutes, with a one-time popup: "15 minutes left. Finish checkout or release the cart.", once per expiry). Ended: the reason and Dismiss.

Authentication

All Fox API calls require two things: session cookies (sscaltoken and JSESSIONID — HttpOnly, set by Fox on login, not accessible to JavaScript) and the CSRF token set as X-CSRF-TOKEN on all mutating requests. The credentials: 'include' fetch option handles cookie forwarding automatically.

Practice Vendor Page (Test)

In the Test package, every vendor key opens practice/practice.html?vendor=<key> instead of the vendor's site. The page plays the role of the vendor site and its content script, so the background, the API and the PWA see the same sequence as on the real vendor. It uses the same overlay code as the Fox script, with the vendor's names from its config, so every pop-up reads exactly as on Fox.

What the User Sees

  • An amber TEST ENVIRONMENT strip, the header Practice cart · Fox Parts, and a LOGIN box at the top right
  • Not logged in: the cart area asks to log in, and the overlay shows the login banner. LOGIN sets the login for the rest of the browser session and reloads the page, which re-checks as a vendor login does
  • Cart tab: lines with part name (from the session's items; Extra item otherwise), code and quantity (+/−, Remove); Add an extra item (any code, quantity 1–999; the same code again adds to its line); Empty cart
  • Checkout tab: the order number, the lines and Place order, which empties the practice cart. The user then clicks I submitted the order on the overlay, as on Fox

Messaging and Security

  • Answers check_identity, fill, read_cart and session_changed only from the background (this extension, no tab, the background's URL) and only when target_tab_id is its own tab. Other runtime messages it receives (the bridge's forwards, other pages) are ignored
  • Sends get_session_view on every load and checkout_entered on Cart → Checkout; the overlay sends overlay_action, warning_shown and dismiss_session
  • Uses only its two storage keys; never reads the session record that holds the callback token
  • Script and styles from files only; all text through textContent

Adding a New Vendor

The background's session logic is vendor-neutral. A new vendor needs its own content scripts and configuration; the manifest entries are generated by the build.

1
Create the vendor directory and config
Create src/vendors/{vendorkey}/vendor.config.js following the Fox pattern, with one named export. vendor_key must match Vendors.Vendor_key; name and site_name are the overlay's wording (also used on the practice page); base_url and cart_page are used by the build and the background.
2
Create content.main.js (if the platform needs it)
Reads page globals the isolated world cannot see. No fetch calls.
3
Create content.isolated.js
Answer the background's messages with the shapes in §04: check_identity → logged_in / login_required / wrong_account; fill → added / add_failed / cart_not_empty / login_required, always with cart_lines (code, quantity, line_id) and vendor_order_id; read_cart. Never delete cart lines. Send get_session_view on load and stay inert without a session; send checkout_entered when the user enters checkout. Draw the overlay with createOverlay from core/overlay.js (vendor names, plus onInCart / onLeftCart to start and stop the cart watch); do not build a vendor-specific overlay.
4
Register in both packages
Add the vendor to vendors in both package definitions: 
// src/packages/live.js — the vendor's site
newvendor: { kind: 'site', config: NEW_VENDOR_CONFIG },

// src/packages/test.js — the practice page (uses only the key and names)
newvendor: { kind: 'page', config: NEW_VENDOR_CONFIG },
The build adds the vendor's host_permissions and both content scripts to the Live package from base_url; the Test package gets no vendor permission. Background and base manifest do not change.
5
Database — vendor records
A Vendors row with the matching Vendor_key, an active VendorOrderMethods row with method = 'web_cart', and VendorParts rows with the vendor's part codes.
6
Build, release, test
npm run build, release a new version (§12), and test from the PWA: in Test on the practice page, and on the real vendor through the Live package (localhost until the Live environment exists): login wait, stop on a non-empty cart, fill, checkout reconcile, I submitted the order, Release cart, countdown.
✅
No API changes required for a new vendor — sessions, the cart lock, reconcile, mark-ordered, release and resolution are vendor-neutral. Only the database records above are needed.

Deployment

A push to main builds, signs and publishes both packages to Azure Storage. An Intune device configuration policy force-installs both on every managed device, and Edge picks up new versions from each package's hosted update manifest. Users do not install them.

Release Pipeline — deploy.yml and release-package.yml

deploy.yml runs on every push to main, and on demand (Run workflow). One run at a time (a newer run waits). No approval step. It runs two jobs, each calling the reusable workflow release-package.yml with its package name and only its own signing key secret:

  • Release test first, then Release live, which runs only after Test has succeeded. If Test fails, Live stays on its current version, so Live never moves ahead of a failed Test release
  • Each package publishes only when the version is higher than its hosted one. If Test published and Live then failed, rerun the workflow: Test's gate skips (not higher) and Live publishes
Step (per package)What it does
BuildNode 24; npm ci; node build.js --package=<package>
Release gatenode scripts/version-gate.mjs --package=<package> takes the extension ID and hosted file names from the package definition and reads the hosted update manifest. Built version higher, or nothing hosted → publish. Equal or lower → the remaining steps are skipped. Missing or invalid extension ID, hosted manifest for a different ID, or any read error other than not found → the job fails. Passes the file names to the later steps
Signing keyPublish only. The job's key secret (PKCS#1) converted to PKCS#8 in /tmp; deleted at the end of the job, also on failure

Versioning

⚠️
Edge installs an update only when the hosted version is higher than the installed one. The only version source is package.json (currently 1.4.1), shared by both packages: a version bump publishes both, no bump publishes neither. Versions compare as Edge compares them: dotted numbers, missing parts count as 0 (1.0.0 equals 1.0). A push without a version bump builds but publishes nothing, so a released version is never replaced by a different build.

Releasing a Version

bash — on main, working tree clean
git commit -m "..."            # the change
npm version patch               # or minor / major: bumps package.json and package-lock.json, commits, tags vX.Y.Z
git push --follow-tags          # the workflow publishes Test, then Live

Patch for fixes, minor for new capabilities, major for breaking changes to the PWA message protocol. Pre-release versions (1.1.0-beta) are not allowed: the build stops.

Each value on its own row, with no spaces before or after. Edge treats a leading space as part of the ID and skips that entry; edge://policy then shows Invalid extension ID for it (seen in November 2026 when the Test value was added). After any change to the policy, check edge://policy → ExtensionInstallForcelist on a synced device: one entry per value, no error in its status.
⛔
Each extension ID comes from its signing key. A package signed with a different key has a different ID, which matches neither the Intune value nor the PWA's extension ID setting. Keep EXTENSION_SIGNING_KEY and EXTENSION_TEST_SIGNING_KEY unchanged; GitHub secrets cannot be read back, so keep a backup of each key outside GitHub.

Rollback

Edge never installs a lower version, and the release gate never publishes one. To undo a release, revert the change and release it with a higher version (npm version patch).
